# 검증 — 어느 수준을 언제 돌리는가

> 검증을 없애기 위한 체계가 **아니다**. 같은 게이트를 "필요한 시점에 필요한 범위만" 돌린다.
> 규칙은 `scripts/verify.sh` 한 곳에 있고 CI 는 그것을 부른다. 목록을 다른 곳에 복제하지 않는다.

## 1. 수준

| 상황 | 수준 | 명령 | 소요 |
| --- | --- | --- | --- |
| 코드 한 덩어리를 고쳤다(개발 루프) | fast | `bash scripts/verify.sh fast` | 수 초 |
| **작업을 끝냈다 / PR 을 올린다** | full | `bash scripts/verify.sh full` | 수십 초 |
| 릴리스 태그를 붙인다 | release | `bash scripts/verify.sh release` | full + 수 초 |

애매하면 한 단계 위. **full 1회 통과 전에는 "완료"라고 보고하지 않는다.**

## 2. 단계별 내용

| 단계 | fast | full | release | 무엇을 잡는가 |
| --- | --- | --- | --- | --- |
| gofmt | ✅ | ✅ | ✅ | 포맷(CI 첫 단계와 동일) |
| go build / vet | ✅ | ✅ | ✅ | 컴파일·정적분석(예제 포함 — 같은 모듈) |
| go test `-short` | ✅ | | | 외부 consumer 빌드(수 초)를 건너뛴 단위 테스트 |

## 3. 개별 실행

```bash
go test ./extension/v1 -run 'TestManifestValidate' -v            # 한 묶음만
go test ./extension/v1 -run TestPublicAPISnapshot                 # 골든 비교
UPDATE_SDK_API_GOLDEN=1 go test ./extension/v1 -run TestPublicAPISnapshot && git diff extension/v1/testdata/api-v1.golden
go test ./extension/v1 -run TestExternalConsumerCompiles -v       # 외부 모듈 빌드
```

## 4. 알아야 할 실패 모드

- **`TestExternalConsumerCompiles` 가 모듈 캐시 문제로 실패**: 네트워크를 쓰지 않는다(GOPROXY=off). `go mod download` 를 한 번 돌리면 yaml.v3 가 캐시에 들어간다. 조용히 SKIP 되지 않는 것이 의도다.
- **골든 불일치**: 의도한 추가면 갱신 후 diff 확인. 줄이 사라졌으면 코드를 되돌린다 → [불변식.md](불변식.md) §2.
- **`TestSDKVersionMatchesChangelog` 실패**: CHANGELOG 최신 `## vX.Y.Z` 와 `compat.go` 의 `SDKVersion` 이 다르다. 릴리스 중이 아니면 CHANGELOG 제목을 잘못 건드린 것이다. 미출시 항목은 `## v` 로 시작하지 않는 제목(예: `## 미출시`)을 쓴다.
- **gofmt 전 파일 미적용 / 골든 전체 diff**: CRLF 체크아웃이다. `.gitattributes` 가 있는지, `core.autocrlf` 를 확인한다.
- **Core 저장소 `sdk/` 안에서 돌릴 때**: `GOWORK=off bash scripts/verify.sh <수준>`. go.work 가 SDK 를 워크스페이스로 끌어들이면 독립 저장소와 조건이 다르다.

## 5. 보고 형식

- 실행한 수준과 결과 요약(`verify.sh` 마지막 표)만 붙인다. 전체 로그를 붙이지 않는다.
- 실패는 **핵심 오류 라인만**. 미실행 단계는 "미검증"으로 명시한다.
- `frontend/v1` 변경은 이 저장소에서 검증할 수 없다 → "Core 에서 `npm run check:bridge` 미검증" 이라고 쓴다.
